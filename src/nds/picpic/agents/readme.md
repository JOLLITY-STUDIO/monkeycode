# {{GAME_NAME}} 逆向转写项目 —— Agent 体系总览

> 本体系是**游戏无关通用模板**。任何游戏（NDS / GBA / NES 等）均可直接套用：
> 角色提示词只讲"方法"不讲"具体游戏"，游戏特有信息（状态码、资源目录、玩法、说明书要点）统一记录在 `game-context.md`，由项目经理(01)在项目初始化时生成。

## 一、任务背景（用户文本原文）

> 如果只给你 rom 和（游戏说明书（如果有）），按项目管理，和逆向工程等软件开发技术、项目规范来完成一个完整体系流程规范收尾,还有工作流转。你会建立那些 agent，把他们按角色提示词 md 文件写入 agents，并把我这些文本写入 agents/readme.md

**任务约束**：
- 输入仅限：ROM 二进制 + 游戏说明书（如有）
- 输出：完整的项目管理体系 + 逆向工程流水线 + 软件开发规范 + 收尾流程 + 工作流转
- 每个角色以独立 md 提示词写入 `agents/` 目录

## 二、如何使用（新游戏套用流程）

```
1. 放置素材：roms/{{ROM_FILE}}（+ docs/{{MANUAL_FILE}} 说明书，如有）

5. 每个大阶段完成 → 里程碑 Tag → 最终交付（不依赖 ROM/汇编）
```

## 六、工作流转（核心闭环）

### 6.1 主流水线（泳道）

```
【输入】ROM + 说明书
   │

   │
   ▼
[02 架构师] 总体架构 → 模块边界 → 接口契约 → 技术选型
   │
   ▼
[03 ROM分析师] Header/文件系统/Bank/资源索引 → ROM_STRUCTURE_REPORT.md
   │
   ▼
[04 反汇编] 主/辅固件反汇编 → 函数表/交叉引用 → 汇编修正(对照CDL/数据)
   │
   ▼
[05 状态机] 状态流转图 → 场景映射 → 事件/子状态表
   │
   ▼
[06 资源提取] 解压/单元分解 → 压缩数据单元 + 调色板 / 精灵 / 地图 / 文本 / 音频（PNG 仅开发期预览）
   │
   ▼
[07 逻辑转写] 核心逻辑汇编→TS（去CPU模拟、数据中台KV化）
   │
   ▼
[08 引擎] 帧循环 / 渲染 / 输入 / 存档 / 数据缓存
   │
   ▼
[09 场景] 按状态机清单逐一实现全部场景
   │
   ▼
[10 平台适配] 目标平台接线与兼容（小程序 / H5 等）
   │
   ▼
[11 测试] 无界面脚本 / 单元测试 / 真机对照
   │
   ▼
[12 审查] 回归审核 → 规范门禁 → 修复循环
   │
   ▼
[13 发布] 版本号 → 里程碑 Tag → Push → 收尾交付
   │
   ▼
【产出】不依赖 ROM/汇编 的目标转写产物
```

### 6.2 迭代闭环（每任务必走）

```
1. 从任务队列取任务
2. 制定该任务子步骤
3. 执行（分析/编码）
4. 单元测试验证逻辑
5. 回归审核（发现任何问题 → 返工到对应上游环节，重新走通）
6. 更新开发日志（进度表/卡点/攻克记录）
7. 更新版本号 → 提交 Push
8. 大阶段完成 → 打里程碑 Tag
9. 重复 1
```

### 6.3 错误与 BUG 反哺（质量回溯）

```
任何环节发现问题（汇编与ROM差异 / 汇编与TS差异 / 数据误判）：
  1. 记入 BUG 文件
  2. 定位责任环节（由 12 审查判定）
  3. 回退到上游 agent 修复（如：反汇编质量差 → 修复汇编文件）
  4. 修复后重跑测试 → 更新 BUG 状态 → 回归审核
```

### 6.5 模拟器黄金帧流水线（Golden Frame Pipeline）

> 目的：用开源模拟器驱动真实 ROM，自动采集**像素级真机画面**作为场景还原的唯一视觉基准，替代"人工截图 + 印象还原"。

| 步骤 | 角色 | 动作 |
|---|---|---|
| 1. 选型 | 11 测试 | 按 game-context 平台选开源模拟器（NDS→melonDS/DeSmuME，GBA→mGBA，NES→Mesen/FCEUX…） |
| 2. 输入脚本 | 11 测试 | 依 05 状态机流转编写自动化输入序列（启动→按键/触屏→帧推进），保证确定性回放 |
| 3. 自动截帧 | 11 测试 | 驱动模拟器逐帧/逐状态截图（NDS 双屏分别截），输出黄金帧库 + 元数据（模拟器版本/ROM hash/输入序列/帧号） |
| 4. UI 规格反推 | 05/06 | 从黄金帧反推每个场景的 UI 规格表（控件坐标/尺寸/颜色/层级/字体），回写 game-context |
| 5. 还原落地 | 09 场景 | 按 UI 规格表 + 06 资源渲染（Canvas 纯渲染） |
| 6. 视觉回归 | 11 测试 | 当前实现渲染帧 vs 黄金帧逐像素/分区 diff，输出差异热图 + 相似度；低于阈值打回 |

**约束**：
- 模拟器/ROM 只用于**采集基准**，最终产物**不依赖**模拟器与 ROM
- 黄金帧库是可追溯资产（版本受控），作为 12 审查与 13 收尾的对照依据
- 无模拟器/截图条件时，退化为 05 分析 + 说明书人工推断，但必须标注"推断"，待黄金帧到位后校准

### 6.6 自动通关与路径覆盖（AutoPlay / Path Coverage）

> 目的：用模拟器自动化驱动游戏从启动到通关——**顶级垂直切片**，作为端到端验收与回归基准；再由反汇编分析补全全路径覆盖。与黄金帧互补：**通关脚本证明"流程通"，黄金帧证明"画面像"**。

| 步骤 | 角色 | 动作 |
|---|---|---|
| 1. 路径覆盖分析 | 04 反汇编 + 05 状态机 | 输出状态可达矩阵 + 分支条件 + 每分支最小输入集（可追溯到状态码/汇编地址） |
| 2. 主干通关脚本 | 11 测试 | 模拟器驱动，确定性输入序列从启动跑到通关 → 垂直切片（证明端到端闭环） |
| 3. 全路径补全 | 11 测试 | 按 04 路径清单逐步触发未覆盖分支，直至 100% 覆盖 |
| 4. 转写等价重放 | 11 测试 | 在转写产物（无头引擎）上重放等价输入序列，逐路径断言状态与关键画面 |
| 5. 验收/回归 | 01/13 | 主干通关脚本为验收 gate，任何改动后回归重跑 |

**约束**：
- 通关脚本必须源自 04/05 分析（每路径可追溯到状态码/汇编地址），禁止"人工瞎点"式生成
- 模拟器回放验证"原版行为"；转写产物重放验证"行为一致"，两者互补
- 覆盖矩阵（路径 × 输入 × 结果）随脚本入库，未覆盖路径明确列出待补
- 最终产物不依赖模拟器/ROM：通关脚本是测试资产，运行时是转写产物自身

## 七、统一规范（所有 Agent 必须遵守）

1. **禁止编造数据**：不得用测试数据替代真实数据，禁止靠猜测；未确证前不做假设
2. **数据来源可溯**：所有声明式数据必须标注来源（ROM 偏移 / 说明书页码 / 反汇编地址）
3. **游戏无关提示词**：角色提示词只含方法论；具体游戏信息一律查 `game-context.md`，不得写入提示词
4. **去硬件模拟**：CPU/PPU/OAM/VRAM 一律转写为 TS 函数/类型/数据中台（类 Redis KV）
5. **二进制零残留**：最终代码不得残留未识别二进制或十六进制硬编码；数据一律声明式结构化，图形一律为"原始压缩字节单元 + 运行时 TS 解码器"（见第 14 条）
6. **面向对象 + 接口访问**：MVC 分层，页面/架构/游戏逻辑分离
7. **文档随代码走**：每个大阶段产出文档（报告/设计/日志/BUG），版本受控
8. **脚本语言**：优先 python / node；避免 powershell/cmd 脚本；合理管理终端，不用时关闭
9. **版本与 Git**：每完成一个任务更新版本号并 Push；每大阶段打里程碑 Tag
10. **资源就绪度分级（占位符策略）**：资源逆向是迭代过程，允许下游先用占位符，但必须：
    - 布局/坐标/尺寸/层级一律来自 ROM 分析/黄金帧（真实），仅纹理/图形可占位，禁止自行发明布局
    - 占位显式标记 `FIDELITY-PENDING`，登记占位符替换清单
    - 资源到位后逐项替换，QA 核对关闭；未清理的占位符不得通过审查与发布
11. **渲染通道约束**：游戏画面一律 Canvas 纯渲染；`page`/`html` 仅作宿主容器，禁止用 HTML 标签（div/span/img…）拼装游戏画面；NDS 双屏 = Canvas 内两个绘制区域（viewport），NES PPU = 瓦片/精灵渲染管线，均非多个页面
12. **双阶段交付**：Phase 1 还原版 = 行为 + 像素级视觉 100% 对齐 ROM，期间禁止 UI 创新；Phase 2 重置版 = 沿用素材资产与核心玩法，界面排版可创新；两阶段任务队列/版本线隔离，Phase 1 未交付前不启动 Phase 2 改动
13. **自动通关验收**：主干通关脚本（垂直切片）必过；发布前路径覆盖矩阵无未覆盖关键路径（可明确豁免并记录）
14. **资源最小化 + Code/Data 分离 + 单元分解**：
    - 游戏包内资源 = ROM 原始压缩数据单元（LZ 等）+ JSON 声明式数据，**禁止 PNG 作为游戏运行时资源**（实测 PNG 体积大于 LZ 压缩原数据，仅增包体）
    - 解码在运行时由 TS 解码器完成（LZ 解压 + 瓦片/调色板/地图/音频解码，Canvas 绘制），解码器复用统一管线
    - PNG 仅作开发期可视化验证（tools/previews/），严禁进入游戏包
    - **Code/Data 分离**：`code/`（引擎/场景/逻辑/解码器）与 `data/`（全部资源数据：images/audio/maps/palettes/text/sprites/meta）物理分层，代码与数据互不混入；代码只通过 `data/index.json` 索引按需加载数据
    - **Data 细切独立单元**：ROM 中一个数据文件可能打包多个资源单元（多瓦片/多帧/多音效/多子块），必须解析内部结构分解为独立单元，每个单元独立文件/模块，按需加载引用；单元清单以 JSON 索引登记（ID/源偏移/大小/类型/依赖）
    - **头文件/元数据 JSON 化**：ROM Header、文件系统分配表、资源索引、偏移映射、场景→资源映射等一律输出为 JSON 结构化数据（`data/meta/*.json`），禁止在代码中硬编码写死
