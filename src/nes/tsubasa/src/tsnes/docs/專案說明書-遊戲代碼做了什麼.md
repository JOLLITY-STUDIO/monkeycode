# 專案說明書：遊戲代碼在做什麼

> 不用懂 6502 彙編，只看 TypeScript 代碼就能理解。

---

## 一、這個專案在做什麼？

把 NES 遊戲《天使之翼 2》從 6502 機器碼翻譯成 TypeScript，讓它能在瀏覽器和微信小程序裡跑。

原版 NES 遊戲的邏輯全寫在 ROM 芯片裡（機器碼），這個專案逐塊把它翻譯成帶註釋的 TypeScript 函數。

---

## 二、遊戲的「一幀」是怎麼出來的？

NES 每 1/60 秒畫一幀畫面，三件事交替執行：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  遊戲邏輯     │ →  │  NMI 畫面更新  │ →  │  PPU 硬體渲染  │
│  (mainLoop)  │     │  (寫入 PPU)   │     │  (掃描線輸出)  │
└──────────────┘     └──────────────┘     └──────────────┘
```

對應到我們的 TypeScript 代碼（見 `test-mock-frame.ts` 第 274-279 行）：

```typescript
// 一幀的完整流程
tick_BANK31_mainLoop(sys);       // ← 跑遊戲邏輯（處理按鍵、計算滾屏、狀態機）
bank02_nmiHandler(sys);           // ← NMI 畫面更新（把要畫的東西寫入 PPU）
bank02_ppuScrollUpdate(sys);      // ← 滾屏 + 這幀結束收尾
ppuStepFullFrame(ppu);            // ← PPU 硬體把資料渲染成 256×240 像素
```

**所以每幀結果 = 遊戲邏輯算出來的畫面內容 + PPU 硬體畫出來的像素。**

---

## 三、每個 bank 文件管遊戲的哪部分？

| 文件 | 對應遊戲功能 | 白話說明 |
|------|-------------|---------|
| `bank-31.ts` | **啟動 + 比賽主循環** | 遊戲開機後初始化，比賽中每幀處理球員移動、足球物理 |
| `bank-02.ts` | **NMI 畫面渲染器** | 每幀結束時把"要畫的東西"從記憶體傳給 PPU 顯示晶片 |
| `bank-00.ts` | **標題畫面 + 腳本引擎** | 管理標題選單、過場動畫、密碼輸入這些"劇本化"的畫面 |
| `bank-30.ts` | **系統庫** | 通用工具：場景切換、調色板、定時器、bank 切換這些底層操作 |
| `bank-01.ts` | **比賽跳轉邏輯** | 比賽中的場景切換、輔助入口 |
| `bank-11/12/...` | **其他場景邏輯** | 特定菜單或場景的處理 |

## 四、mock 測試到底在跑什麼？

`test-mock-frame.ts` 做的是**從零啟動遊戲引擎，看看 bank 翻譯代碼能不能跑通**。

```typescript
// Phase 2: 模擬 NES 開機 → 執行 RESET 程序
translate_BANK31_RESET(sys);

// Phase 5: 連續跑 100 幀
for (let frame = 1; frame <= 100; frame++) {
    tick_BANK31_mainLoop(sys);      // 遊戲邏輯
    bank02_nmiHandler(sys);          // 畫面更新
    bank02_ppuScrollUpdate(sys);     // 滾屏收尾
    ppuStepFullFrame(ppu);           // PPU 渲染成像素
    // → 保存為 BMP 圖片
}
```

**問題：為什麼 100 幀畫面都一樣？**

因為標題畫面的"構建"是一個**多幀腳本**，不是一幀畫完的：

```
幀 1-2:    寫入調色板（決定用什麼顏色）
幀 3-40:   等待延遲 + 淡入效果（畫面慢慢亮起來）
幀 41-80:  逐行寫入上半部分（標題文字 + 密碼框）
幀 81-100: 逐行寫入下半部分（50 音鍵盤）
```

我們的 mock 雖然跑了 100 幀，但**中間某個條件判斷翻錯了**，導致腳本引擎卡住，畫面一直停留在第 1-2 幀的調色板狀態。

這不是 PPU 的問題，是 `bank-00.ts` 裡面的**字節碼解釋器**（bytecode script engine）翻譯有 bug。

## 五、畫面從哪來的？（這些數據具體在哪個檔案、哪個變數裡）

NES 畫面由兩層疊加：

### 5.1 三層數據的存放位置

```
                                                ┌─────────────────────────┐
                  sys.mem[0x0200 ~ 0x02FF]  →   │  精靈層 (OAM, 256 bytes) │
                  (CPU 記憶體中的第 2 頁)          │  每個精靈 4 bytes:        │
                  bank-02.ts NMI 開頭:             │  Y座標, tile編號, 屬性, X座標│
                  writeMem(sys,0x4014,0x02)       └─────────────────────────┘
                           ↓                              ↓
                  ppu.spriteMem[0 ~ 0xFF]        ppu 解碼成:
                  (PPU 內部 OAM 副本)              sprX[64], sprY[64],
                                                  sprTile[64], sprCol[64]...
                                                ┌─────────────────────────┐
                  ppu.vramMem[0x2000 ~ 0x2FFF] →│  背景層 (Nametable)       │
                  (PPU VRAM 中的背景區)            │  1024 bytes 的背景佈局     │
                  寫入入口:                       │  每個 byte = 一個 tile 編號 │
                  writeMem(sys, 0x2007, data)    └─────────────────────────┘
                           ↓
                  數據來源: sys.mem[0x05E8 ~ ]
                  (bank-00.ts 腳本引擎填入)
                                                ┌─────────────────────────┐
                  ppu.vramMem[0x0000 ~ 0x1FFF] →│  圖塊表 (Pattern Table)   │
                  (PPU VRAM 中的圖形區)            │  所有 8×8 像素小圖標       │
                  來源:                         │  每個 tile = 16 bytes     │
                  tsubasa-hex2asm/              └─────────────────────────┘
                    chr_banks/bank_0_8k.ts
                         ~
                    chr_banks/bank_15_8k.ts
                  (共 16 個 bank, 各 8KB)
```

### 5.2 對應的 TypeScript 檔案和行號

| 你要找的 | 在哪裡 | 是什麼 |
|---------|--------|--------|
| **精靈數據源頭** | `sys.mem[0x0200]` ~ `[0x02FF]` | bank 代碼直接寫這個記憶體區（放角色、光標的位置） |
| **精靈傳給 PPU** | `bank-02.ts` 第 76-79 行 | `writeMem(sys, 0x2003, 0)` + `writeMem(sys, 0x4014, 0x02)` → 觸發 DMA，把 `sys.mem[0x0200+]` 複製到 `ppu.spriteMem[]` |
| **精靈 PPU 存儲** | `ppu/index.ts` 第 24 行 | `this.spriteMem = new Uint8Array(0x100)` |
| **精靈渲染用的解碼後數據** | `ppu/index.ts` 第 110-118 行 | `this.sprX[64]`, `this.sprY[64]`, `this.sprTile[64]` 等 |
| **背景 PPU 存儲** | `ppu/index.ts` 第 23 行 | `this.vramMem = new Uint8Array(0x8000)`，背景在 `[0x2000..0x2FFF]` |
| **背景數據隊列（誰填）** | `sys.mem[0x05E8]` ~ `[0x0627]` | `bank-00.ts` 的字節碼解釋器把「要畫什麼」填進這裡 |
| **背景寫給 PPU** | `bank-02.ts` 第 100-149 行 | NMI handler 讀取隊列，逐條 `writeMem(sys, 0x2007, data)` 寫入 PPU |
| **圖塊表原始數據** | `tsubasa-hex2asm/chr_banks/bank_0_8k.ts` ~ `bank_15_8k.ts` | ROM 裡的圖形數據（從 .nes 檔案拆出來的，每個 bank 8KB） |
| **圖塊表 PPU 存儲** | `ppu/index.ts` 第 23 行 | 同上 `this.vramMem`，圖形在 `[0x0000..0x1FFF]`（由 mapper 把 CHR-ROM 映射進來） |
| **最終每一幀的輸出** | `ppu/index.ts` 第 96-97 行 | `this.buffer = new Uint32Array(256*240)` ← 這就是 BMP 的來源 |
| **調色板** | `ppu/index.ts` 第 23 行 | `this.vramMem[0x3F00..0x3F1F]`（32 bytes，決定每個像素最終顏色） |

### 5.3 一句話串起來

```
CHR-ROM 檔案(tile 圖形) → mapper 載入 → ppu.vramMem[0x0000~0x1FFF]
                                                  ↓
bank-00.ts 腳本 → 填 sys.mem[0x05E8+]  → bank-02.ts NMI → writeMem(0x2007) → ppu.vramMem[0x2000+]
bank 代碼      → 填 sys.mem[0x0200+]    → NMI DMA       → ppu.spriteMem[]
                                                  ↓
PPU 每條掃描線讀取上面三個數組 → 畫入 ppu.buffer[256×240] → 輸出像素
```

## 六、trace 日誌和 bank 代碼怎麼對應？

`trace/first-f2645-summary.txt` 是**真機 FCEUX 模擬器跑的記錄**。每一行記錄：遊戲執行了哪條機器指令、PPU 收到了什麼數據。

**跟我們的 bank 代碼關係：**

```
trace 記錄:  $01:A175  →  執行了 bank 01 裡地址 $A175 的代碼
                              ↓
我們的代碼:  bank-01.ts  裡面某個函數
```

trace 是用來**對照驗證**的：真機跑了某條指令，我們的 TypeScript 翻譯有沒有產生一樣的結果。

舉例，trace 中第 5 行：
```
PPU_SCROLL = #$02    →  螢幕滾動位置 X=0, Y=2
PPU_SCROLL = #$00
```

這表示真機在那一幀把畫面向右移了 0 像素，向下移了 2 像素。

## 七、記憶體中幾個關鍵「開關」

遊戲狀態存在記憶體陣列 `sys.mem[]` 中：

| 地址 | 名稱 | 作用 |
|------|------|------|
| `$0628` | 渲染隊列長度 | = 0 表示「這一幀沒東西要畫」，NMI 直接跳過 |
| `$0629` | PPU 忙碌標誌 | bit6=1 表示 PPU 上一幀數據還沒傳完，不寫入 |
| `$0027` | 場景子狀態 | =0 標題畫面, =1 菜單, =3 過場動畫… |
| `$004A` | 亮度 | =0 全黑, =32 正常亮度（淡入淡出效果） |
| `$05E8+` | PPU 寫入隊列 | 每幀要傳給 PPU 的畫面數據（最多約 60 字節） |

**所以 mock 測試 log 中如果 `$0628=0`，就表示那一幀腳本沒有產生任何畫面數據。**

## 八、一句話總結

| 你看到的 | 對應的是 |
|---------|---------|
| BMP 圖片沒東西 | 腳本引擎沒推進 → `$0628` 一直是 0 → NMI 無數據寫入 PPU |
| mock 跟真機對不上 | 中間某個 bank 函數的邏輯翻譯錯了 |
| trace log 裡 `A=$xx` | 那是 6502 CPU 的變量值，對我們來說 = 函數的參數/返回值 |
| `$01:A175` | bank-01.ts 裡對應位置有一段處理 PPU 滾動的代碼 |
