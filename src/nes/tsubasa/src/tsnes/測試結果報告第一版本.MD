## 根因分析 (2026-07-28)

### 核心問題
字節碼引擎從 bank 0 的 $8000 讀取 6502 機器碼當作腳本數據執行，而非真正的字節碼腳本。

**場景註冊表 (scene-registry.ts) 中** TECMO_LOGO (0x00)、TITLE (0x02)、LOAD_GAME (0x03)、MAIN_MENU (0x04) 都設置為 `bank: 0, scriptAddr: 0x8000`，但 bank 0 的 $8000 是 dispatch 引擎自身的 6502 機器碼，不是腳本數據。

### 惡性循環鏈路
1. `boot()` → `dispatchIndex=0` → `initScene(0)` → `dispatchIndex=1`
2. `_runBytecodeEngine()` 從 bank 0 $8000 讀 6502 指令碼
3. 機器碼字節 $E8 (INX)/$F9 (SBC abs,Y) 被誤解為 SCENE_TRANS/FADE_SCENE
4. `dispatchIndex=4` → `sceneId++` → `dispatchIndex=0` → 回到步驟1
5. 每 2-3 幀递增一次 sceneId，數秒內飙到 153+

### 畫布黑屏原因（三重）
1. **調色板**: `paletteBuffer.fill(0x0F)` — 全部黑色 (NES color 0x0F = RGB 0,0,0)
2. **Nametable**: 機器碼當文本輸出，寫入的是無效 tile，nametable 全為垃圾數據
3. **Canvas API**: `putImageData` + 同源 `drawImage(canvas, ...)` 在微信小程序 Canvas 2D 不兼容

## 修復記錄 (2026-07-28)

### 修復1: scene-registry.ts — 跳過無效腳本場景
- 新增 `_hasValidScript()` 檢查：`bank=0 && addr=0x8000` 的場景視為無效，不進入字節碼引擎
- 新增 `MAX_SCENE_ID = 0x20` 上限：超出範圍強制結束
- 無效/未知場景設 `dispatchIndex=4` 自動跳到下一場景
  → sceneId 0→2→3→4→5 (自動跳過 Logo/Title/Menu，直達 STORY_INTRO)

### 修復2: scene-manager.ts (boot) — 默認調色板
- 將全 0x0F (黑) 改為彩色默認調色板（白/紅/藍/橙/綠/粉等）
- 確保在加載真實 ROM palette 前畫布也有可見內容

### 修復3: scene-manager.ts (_defaultDispatch) — scene 溢出防護 + 修正 dispatchIndex 覆蓋
- `dispatchIndex=4` 路徑增加 sceneId 上限檢查
- 超过 0x20 時輸出警告並設 `dispatchIndex=5`（結束遊戲）
- **修正**: 刪除 `idx=0` 路徑中的 `s.dispatchIndex = 1` 強制賦值
  - 原因：`initScene()` 已根據場景有效性設置 dispatchIndex (1=bytecode, 4=skip)
  - 舊代碼無條件覆蓋為 1，導致無效場景無法跳過 → 一直卡在 scene=0 dispatch=1

### 修復4: canvas-renderer.ts — 微信小程序 Canvas 兼容
- `getContext('2d')` 增加 try/catch：WX 可能不支持 `{ willReadFrequently }`
- 移除 `drawImage(canvas, ...)` 自引用調用：WX Canvas 2D 不支持同源 self-drawImage
- 直接使用 `putImageData`，canvas 尺寸 = NES 分辨率無需縮放

### 狀態: 已修復，待驗證

## 第二次驗證 (2026-07-28) — 修正 dispatchIndex 覆蓋

**問題**: 第一次修復後 scene 依然卡在 0, dispatch=1。
**根因**: `_defaultDispatch` 中 `idx=0` 路徑在 `initScene()` 後無條件執行 `s.dispatchIndex = 1`，
覆蓋了 `initScene` 設置的 `dispatchIndex=4`（跳過無效場景）。
**修復**: 刪除該行，讓 `initScene` 的設置生效。
**結果**: scene=5, dispatch=1 ✓ (已正確到達)，但畫面全白 ✗

**第三次驗證日誌分析**:
- `bc#0-7`: 0x20,0xA0-0xA2,0x26,0xA6,0xB4,0xA6 → character literals + 控制碼
- `bc#18`: 0xF1 = BANK_LOAD, arg=0xB1 → **bank6=177** (非法！只有 0-31 bank)
- **0x20 0xA0 0xA1 在 6502 中是 `JSR $A1A0`！**
- 畫布全白：測試圖案被後續 `_renderBackground` 覆蓋 (tile 0 + palette[0]=0x20=淺灰)

**根因**: bank 3 在 0x8000 存的**不是 H5 bytecode，而是原始 6502 機器碼**。
H5 bytecode 引擎把 6502 指令當成 bytecode 在跑。
