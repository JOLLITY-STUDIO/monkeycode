## FAQ-003: 为什么有些数据文件看起来是"空的"？(2026-08-05)

- **日期**: 2026-08-05
- **分类**: 数据来源
- **问题**: PlayerData.ts, MatchSequence.ts 等文件里面只有 TODO 占位，数据去哪了？

### 回答

之前这些文件包含的是**编造的数据**，不是从 ROM 中实际提取的：
- 球员名字是猜测的罗马音

根据项目核心原则，**所有数据必须从 ROM 中实际提取和验证**。
这些文件已被清空为占位结构，等待 ROM 分析后再填充真实数据。

## FAQ-001: TS项目是否需要一个"二进制解析器"？

- **日期**: 2026-08-04
- **分类**: 架构设计 / 项目方向
- **问题**: 如果我们TS项目要全部转成二进制，那是不是要一个解析器？

### 简短回答

**不需要运行时二进制解析器。** 项目的方向是纯 TypeScript 源码重写，不是把 TS 编译成二进制 ROM 再解析运行。

### 详细解释

#### 1. 项目本质：源码级重写（Port），不是模拟器

```
原始 NES ROM (二进制)
    │
    ▼ (离线分析)
反汇编 ASM + CDL 标记
    │
    ▼ (人工理解语义)
TypeScript 源码（游戏逻辑 + 结构化数据）
    │
    ▼ (tsc 编译)
JavaScript (微信小程序运行时直接执行)
```

**关键区别**：

| | 模拟器方案 | 我们的方案（源码重写） |
|---|---|---|
| 运行时依赖 | 需要 ROM 文件 | 不需要 ROM，纯 TS 代码 |
| 执行方式 | CPU 指令模拟（逐条解释 6502 指令） | JS 引擎原生执行 |
| 数据格式 | 运行时读取 ROM 字节 | 编译时声明为 TS 常量/枚举 |
| 是否需要解析器 | 需要 ROM 解析器读取二进制 | 不需要 |

#### 2. 我们实际需要什么？

**构建时工具**（离线运行，不在运行时）：
- `scripts/export_chr_banks.py` — 从 CHR ROM 提取 tile 数据 → 生成 `src/data/chr/*.ts`
- `scripts/read_bank0_table.py` — 从 PRG ROM 提取跳转表 → 生成 TS 结构
- 这些 Python 脚本是**开发工具**，产物是**纯 TS 源码**

**运行时不需要任何二进制解析**：
- CHR tile 数据 → 已声明为 `src/data/chr/chr-bank-00.ts` 中的 `Uint8Array`
- 球员数据 → 已声明为 `src/data/PlayerData.ts` 中的 TypeScript 对象
- 游戏逻辑 → 纯粹的函数和类

#### 3. 类比理解

这就像：
- **模拟器** = 你拿着一张照片（ROM），用一个设备（模拟器）实时解读照片内容
- **源码重写** = 你看着照片，用画笔重新画一幅画（TypeScript 代码），以后直接展示这幅画

我们不需要"解析器"来解读自己的画，因为画本身就是我们用 TS 语言表达的。

#### 4. 如果你的意思是"TS编译成二进制再给其他程序用"

那是完全不同的场景（比如 WASM），但微信小程序本质上就是运行 JavaScript，不需要中间二进制格式。小程序框架自带的 JS 引擎（V8/JavaScriptCore）就是天然的执行环境。

## FAQ-002: CHR 数据为什么要用 JSON 而不是 32 个 TS 文件？

- **日期**: 2026-08-04 (更新 v1.1.0)
- **分类**: 渲染架构
- **参见**: BUG-012, BUG-014, BUG-015

### 回答

**v1.1.0 最新方案**: CHR ROM 数据从 `src/data/chr-data.json` (394KB) 通过 `require()` 加载。

**演进过程**:
| 版本 | 方案 | 问题 |
|------|------|------|
| v0.9.x | CHR → PNG → drawImage → getImageData → 调色板映射 | 128 个离屏 Canvas，性能极差 |
| v1.0.0 | CHR → 32 个 TS 文件 → base64 嵌入 | TS 文件过大 (816KB)，小程序编译失败 |
| **v1.1.0** | **CHR → 单个 JSON 文件 → require() 加载** | ✅ 解决了模块加载失败 |

**当前工作原理**:
1. CHR ROM 原始数据 (32 banks × 4096 bytes) 在 `src/data/chr-data.json`
2. `TileStore.init()` 通过 `require()` 加载 JSON → 2BPP 解码为像素索引
3. Renderer 直接像素索引 → 调色板查表 → ImageData

**为什么不继续用 32 个 TS 文件？**
微信小程序 TypeScript 编译器处理 33 个文件的大依赖链时失败（BUG-015）。
单个 394KB JSON 文件通过 `require()` 加载无此问题。

## FAQ-003: 为什么不用 Package.json 的 npm 依赖？

- **日期**: 2026-08-04
- **分类**: 开发环境
- **问题**: 小程序不需要 npm install

### 回答

由于开发环境中 npm 安装存在问题，项目采用规避策略：
- 所有 TypeScript 源码直接编译，不依赖 npm 包（除微信小程序自带的 WX API）
- 测试文件使用 `.mjs` / `.cjs` 格式直接用 Node.js 运行，不需要 package.json 配置

## FAQ-004: 反汇编质量到底有没有问题？

- **日期**: 2026-08-04
- **分类**: 代码分析
- **问题**: 之前说反汇编有数据误解释为代码，但游戏开始就跑到的代码怎么可能翻译错？

### 回答

**核心6502代码的反汇编完全正确。** BUG-001 的原始描述不够精确，已在 v1.2.1 修正。

实际情况：
| 区域 | CDL标记 | 反汇编质量 | 说明 |
|------|---------|-----------|------|
| Bank 0 Reset/NMI/主循环 | `C` (code) | ✅ 正确 | 标准6502指令，BZK+CDL完美处理 |
| Bank 0 跳转表 ($8000-$809A) | `C`/`D` 混合 | ✅ 正确 | 少量未使用条目被正确标记为data |
| Bank 1-6 代码区 | `C` (code) | ✅ 正确 | CDL正确追踪了执行流 |
| Bank 7 脚本引擎 | `C` (code) | ✅ 正确 | 脚本解释器代码反汇编正确 |
| Bank 7 字节码数据 | `D` (data) | ✅ 正确 | 这是自定义脚本字节码，应该标记为data |

**唯一需要额外处理的是**：Bank 7 中的脚本字节码（非6502指令集），需要M5阶段单独逆向其格式。这不是反汇编的"错误"，而是游戏开发者设计了一套自己的指令集，不能用6502反汇编来解读。
