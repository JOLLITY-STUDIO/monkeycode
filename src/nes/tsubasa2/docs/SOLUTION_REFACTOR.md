# NES 游戏 H5 重写方案（全新 v2）

> 面向问题：6502 不能翻译成 TS、bank 切换与 MMC3 复杂、code 与 data 混合、data 无格式、
> 流程流转复杂、重写后游戏不能保持正常运行。
>
> 核心立场：**不做 6502 翻译，做"拆解 + 重写"。**
> 游戏 = 内容层（数据）+ 逻辑层（行为）+ 壳层（渲染），三层各司其职，单向依赖。

---

## 1. 为什么逐指令翻译必然失败（先定性）

NES 的 6502 程序里，三类东西交织在同一个地址空间：

| 类别 | 内容 | 特征 |
|---|---|---|
| 数据 | 数值表、指针表、脚本流、地图、字符集、调色板 | 无 schema，格式藏在读取代码里 |
| 算法 | 查表换算、位运算、除法学 | 与"用哪个寄存器、哪个标志位"耦合 |
| 流程 | 帧循环、中断、场景切换、菜单状态机 | 函数被 bank 切换物理拆散 |

逐指令翻译 = 把这三者的**交织状态**原样搬进 TS，结果必然是：

1. 代码里全是地址和字节，等于换了个语法重写汇编，还是 CPU 视角；
2. bank 切换把函数拆到不同 8KB 块，翻译后调用关系破碎、跳来跳去；
3. 数据格式只存在于读取指令里，脱离 CPU 上下文根本读不懂；
4. 没有验证手段，改一处崩全局，无法定位。

**结论：翻译保留的是"结构"，而结构恰恰是 NES 硬件强加的，H5 不需要它。
要保留的只有"行为"。行为 = 读哪些数据、算什么、写哪些状态。**

## 2. 全新架构：三层单向依赖

```
┌─────────────────────────────────────────────┐
│  壳层 shell/   帧循环 · 输入 · 渲染适配       │  ← 唯一允许碰"字节/画面"的地方
├─────────────────────────────────────────────┤
│  逻辑层 systems/ 菜单 · 剧情 · 比赛 · 音频    │  ← 业务行为，只读内容层、只写 GameState
├─────────────────────────────────────────────┤
│  内容层 content/ 球员表 · 队伍表 · 脚本 · 地图 │  ← 从 ROM 提取的纯净数据，只读
└─────────────────────────────────────────────┘
```

- **内容层（content）**：唯一"从 ROM 搬"的东西。全部是具名 TS 表/对象，字段有名字。
- **逻辑层（systems）**：用 TS 重新设计业务行为。只消费内容层数据，只读写自己的状态。
- **壳层（shell）**：帧循环、输入采集、把 GameState 转成渲染字节交给渲染器。
  （渲染器可复用现有模拟器 PPU 的绘图能力，但壳层之外谁也不碰它。）

依赖规则：**壳 → 逻辑 → 内容，单向，禁止回头。**
规则落地 = 目录隔离 + import 边界 + 编译期检查（见 §7）。

## 3. 内容层：数据提取 SOP（解决"data 没有具体格式"）

数据格式的唯一真相来源是**消费它的代码**。SOP：

1. **找消费方**：在反汇编里列出所有访问该数据的指令
   （`LDA addr,X` / `LDA (ptr),Y` / 指针表跳转），汇总访问模式。
2. **推断 schema**：按访问模式对号入座：

   | 访问模式 | schema | TS 形态 |
   |---|---|---|
   | 固定基址 + 索引 | 数组 | `const PLAYERS: PlayerRow[]` |
   | 指针（两字节）+ 偏移 | 对象/结构 | `const TEAMS: { id, roster, formation }` |
   | 首字节 + 变长数据 | 记录流 | `const ITEMS: RecordStream[]` |
   | 顺序读到结束符 | 脚本流 | `const SCRIPTS: number[][]` |

3. **写一次性提取脚本**（生成器，标注"一次性工具"，不进交付物），
   输出 `content/` 下的具名表，字段名从消费方代码语义命名。
4. **双人复核**：提取表 vs ROM 原始字节逐字节差分，必须 0 差异。
5. **冻结**：进 content 后任何人禁止再碰裸字节，只能通过表的具名访问。

> 一条数据块，若找不到任何消费方，**不提取**（可能是未用数据，避免编造格式）。

## 4. 逻辑层：行为重写规范（解决"6502 不能翻译"）

翻译单位 = **子程的行为（副作用）**，不是指令。

一个子程 = 一个方法，方法名 = 它做什么；输入输出 = 具名数据，不是内存地址。

```
LDA $C000,X; ...  STA $0454    →   player.gainExp(amount)
```

**映射表（JSR/跳转/协程 → TS）：**

| 6502 结构 | TS 表达 |
|---|---|
| 子程序 `JSR/RTS` | 方法调用 |
| 跳转表（`JMP (table,X)`） | `switch` / `Map<id, fn>` |
| 协程让出 1 帧（`JSR 让出`） | 状态机字段（`this._phase`）或生成器 |
| 零页指针间接读数据 | 具名表查询 `table.find(...)` |
| 帧时序副作用（渐显/滚动/精灵上屏） | 逻辑层只改状态，壳层在帧尾统一提交 |

**禁止项（逻辑层内）：** 寄存器、标志位、内存地址、字节数组、bank 概念。
这些词出现即不合格。

## 5. 流程建模：场景机（解决"流程流转复杂"）

NES 的流程 = 主循环 + 每帧回调 + 场景切换。重写为**场景状态机**：

```ts
interface Scene {
  id: SceneId;
  init(ctx: GameContext): void;   // 进入场景
  update(ctx: GameContext): void; // 每帧逻辑
}
```

- 场景切换 = 显式调用 `sceneMachine.switchTo(sceneId)`，无隐式跳转。
- 一个场景一个模块（Title / Menu / Password / Story / Match），不跨模块。
- 跨场景数据（当前球队、章节、比分）全部放在 **GameContext**（单一状态对象），
  场景只能读自己 + 调 Context 公开接口，禁止互相摸对方的字段。
- 帧管线固定为：`输入采集 → 当前场景 update → 帧尾提交渲染数据 → 渲染`，
  任何场景不得绕过该管线直接写渲染字节。

## 6. 迭代方法：Strangler 模式（解决"重写后游戏不能正常运行"）

**核心保证：任何时刻游戏都能完整跑。**

```
模拟器路径（完整可用，标准答案）
   ▲ 每段双跑对比，通过才切换
新代码路径（逐段生长）
```

**保留模拟器（如 tsnes）作为 oracle 和兜底，不删。** 开发期两条路径共存：

1. **切玩家链路**：`boot → 标题 → 菜单 → 密码 → 剧情 → 比赛 → 终场`
2. **黄金轨迹**：模拟器跑该段，记录"关键状态 + 每帧画面摘要"
   （输入序列固定，输出序列 = 验收基准）
3. **重写该段**：内容层数据 + 逻辑层行为，一次只写一段
4. **双跑对比**：同一输入序列，同时跑模拟器与新代码，对比状态与画面
5. **过闸合并**：一致 → 该段切换走新代码，游戏继续可跑；
   不一致 → diff 定位，修完再切；
   实在卡住 → 该段继续走模拟器，**不阻塞后续段**。

**为什么不会"越改越乱"：**
- 问题被隔离在"当前段"，双跑 diff 直接指出差异点，不用全库猜；
- 未完成的段保持模拟器行为，游戏永远完整可用、随时可演示；
- 每个过闸段 = 一个可玩版本，天然可提交、可回滚到上一个版本。

## 7. 验证体系：三层把关

| 层 | 验证 | 工具 |
|---|---|---|
| 内容层 | 提取表 vs ROM 字节 0 差异 | 一次性差分脚本 |
| 逻辑层 | 行为单测（给定输入状态 → 期望输出状态） | node 测试脚本 |
| 集成层 | 双跑对比（模拟器 vs 新代码，同输入比输出） | 对比脚本 |

**提交闸门**：git 提交前跑一条验证命令，全绿才允许合入。
编译期再加一道 import 边界检查：逻辑层/内容层目录不得 import 壳层与模拟器。

## 8. 里程碑：按玩家链路推进，每阶段可玩

| 版本 | 内容 | 可玩性 |
|---|---|---|
| M1 | boot → 标题画面可见（纯内容层 + 壳层渲染） | 能看到画面 |
| M2 | 标题菜单可交互（新游戏/继续） | 能进菜单 |
| M3 | 剧情脚本播放器（脚本表 + 逐段播放） | 能看剧情 |
| M4 | 密码/存档 | 能存取 |
| M5 | 比赛（阵容 → 开球 → 回合 → 进球 → 终场） | 能踢球 |
| M6 | 全链路串通 + 性能 + 包体积 | 完整游戏 |

每个 M 都过 §6 的双跑验收，不做完上一个不开始下一个。

---

## 9. 工程纪律

1. 内容层禁裸字节；逻辑层禁内存寄存器/地址；壳层才允许碰渲染字节。
2. 一次只动一段；每段提交前必须跑验证闸门。
3. 提取脚本一律标"一次性工具"，用完即删，不进交付物。
4. 模拟器代码与新代码分目录、互不 import（除 oracle 对比工具）。
5. 新增逻辑必须先有"消费方"，禁止凭空写数据。

---

## 10. 团队并行（可选）

- **内容组**：按表分包（球员表 / 队伍表 / 脚本表 / 地图表 / 音频表），各自提取 + 复核。
- **逻辑组**：按场景分包（菜单 / 剧情 / 比赛），只消费 content 接口。
- **集成组**：维护双跑对比工具，卡点即反馈，负责过闸合并。

内容表接口 + 场景模块接口 = 天然分工边界，三组可并行互不阻塞。
